# System Guide

## 1. How the application is organised

The application uses a straightforward three-part structure:

1. **React frontend** — the screens staff use in a browser.
2. **Express API** — receives requests, checks permissions and validates input before applying workflow rules.
3. **PostgreSQL database** — stores user accounts, patient records, appointments, radiology orders, reports and audit events. Prisma is used to access the database.

The usual request flow is:

```text
Staff browser
    ↓
React page and API client (Axios)
    ↓  Authorization: Bearer <JWT>
Express route
    ↓
Authentication → role authorization → request validation
    ↓
Controller → service/business rules
    ↓
Prisma
    ↓
PostgreSQL
```

The frontend is not the security boundary. Hiding a button makes the screen easier to use, but the backend must still reject requests that a role is not allowed to perform.

## 2. Main frontend areas

| Page | Purpose |
|---|---|
| Dashboard | Displays live counts for patients, today's appointments, pending orders, completed exams and reports, plus upcoming appointments. |
| Patients | Lists and searches patient records, registers patients and opens a profile with appointment and order history. The profile also supports demographic editing. |
| Appointments | Lists appointments, filters by date/modality/status, schedules and reschedules appointments, and presents permitted status actions. |
| Radiology Worklist | Lists orders, filters by modality/priority/status, creates orders, shows order details and presents normal or administrator-only status changes. |
| Radiology Reports | Lists reports, creates drafts, edits eligible drafts, opens report details, and provides review/finalization actions to authorized radiologists. |
| Staff Management | Admin-only invitation page. Administrators can invite staff, view invitation status and revoke a pending invitation. It is not a full staff directory. |

## 3. User roles and access

The current staff roles are `ADMIN`, `RECEPTIONIST`, `RADIOLOGIST`, `TECHNICIAN` and `PHARMACIST`.

| Capability | Admin | Receptionist | Radiologist | Technician | Pharmacist |
|---|:---:|:---:|:---:|:---:|:---:|
| Sign in and view dashboard | Yes | Yes | Yes | Yes | Yes |
| View/search patients | Yes | Yes | Yes | Yes | Yes |
| Register or edit patient | Yes | Yes | No | No | No |
| View and list appointments | Yes | Yes | Yes | Yes | Yes |
| Create/reschedule appointments | Yes | Yes | No | No | No |
| Change appointment status | Yes | Yes | No | Yes | No |
| View/list radiology orders | Yes | Yes | Yes | Yes | Yes |
| Create radiology orders | Yes | Yes | No | No | No |
| Change normal order status | Yes | No | No | Yes | No |
| Override order status with reason | Yes | No | No | No | No |

The table describes the route permissions currently visible in the backend. It does not imply that future modules (for example, pharmacy or medication management) are already available. Patient accounts are not part of the current staff-role model.

## 4. Main workflow rules

### Patient records

- A patient is created with first name, last name and date of birth.
- Sex, phone, email and address are optional.
- A patient number is generated by the backend.
- The backend checks for a possible duplicate using first name, last name and date of birth. A possible match returns a conflict response so staff can check the existing record.
- Patient records can be searched by first name, last name or patient number and are returned with pagination.
- The patient profile includes related appointments and radiology orders.

### Appointments

An appointment belongs to a patient and records its scheduled date/time, modality, procedure, optional location and notes, current status and the staff member who created it.

Appointment statuses:

`SCHEDULED → CONFIRMED → CHECKED_IN → COMPLETED`

Other permitted transitions are:

- `SCHEDULED` can move to `CONFIRMED`, `CHECKED_IN`, `CANCELLED` or `NO_SHOW`.
- `CONFIRMED` can move to `CHECKED_IN`, `CANCELLED` or `NO_SHOW`.
- `CHECKED_IN` can move to `COMPLETED` or `CANCELLED`.
- `COMPLETED`, `CANCELLED` and `NO_SHOW` are closed states and cannot be rescheduled through the normal update endpoint.

New appointments must be scheduled in the future. A date range filter cannot have a start later than its end.

### Radiology orders and worklist

A radiology order belongs to a patient and can optionally be linked to an appointment. It includes a unique accession number, modality, procedure, clinical note, priority and status.

Supported modalities:

`XRAY`, `CT`, `MRI`, `ULTRASOUND`, `MAMMOGRAPHY`, `PET_CT`, `OTHER`

Priorities:

`ROUTINE`, `URGENT`, `STAT`

Normal order status transitions:

- `ORDERED` → `SCHEDULED`, `IN_PROGRESS` or `CANCELLED`.
- `SCHEDULED` → `IN_PROGRESS` or `CANCELLED`.
- `IN_PROGRESS` → `COMPLETED` or `CANCELLED`.
- `COMPLETED` and `CANCELLED` are closed states.

An order linked to an appointment must use the same patient and modality as that appointment. The appointment must not already be cancelled, completed or marked no-show.

An administrator can use the separate override endpoint to correct an order status where an allowed override transition exists. The override requires a reason and creates an audit event.

### Radiology reports

A report belongs to one radiology order and has an author. Only a completed order can receive a report, and only one report can be created for an order.

Report statuses:

`DRAFT → REVIEWED → FINALIZED`

- A radiologist creates a draft report.
- Only the original author can edit that draft.
- Both findings and impression must be non-empty before review.
- A radiologist cannot review their own report; a different radiologist must perform the review.
- Only a reviewed report can be finalized.
- Finalized reports are not editable through the current API.
- Important report actions are recorded in the audit log.

### Staff invitations

- Only an active administrator can create, list or revoke invitations.
- Invitations can be issued to `RECEPTIONIST`, `RADIOLOGIST`, `TECHNICIAN` or `PHARMACIST`; this endpoint does not allow inviting another administrator.
- An invitation expires after 24 hours.
- The raw invitation token is returned once when the invitation is created. The database stores its SHA-256 hash, not the raw token.
- The invitee sets a password to activate the account. Reusing an accepted or revoked invitation is rejected.

## 5. Database model at a glance

The authoritative schema is `prisma/schema.prisma`. The main entities and relationships are:

| Entity | Purpose and relationships |
|---|---|
| `User` | Staff account, role, active flag and password hash. Can create appointments, author reports, create invitations and act on audit events. |
| `StaffInvitation` | Invitation details, assigned staff role, token hash, status, expiry and administrator who sent it. |
| `Patient` | Patient number and demographic/contact details. Has appointments and radiology orders. |
| `Appointment` | Patient appointment, creator, scheduled time, modality, procedure, location, status and notes. Can have related orders. |
| `RadiologyOrder` | Accession number, patient, optional appointment, modality, procedure, priority and status. Can have one report and one study link. |
| `RadiologyReport` | One report per order, author, findings, impression, status and finalization timestamp. |
| `StudyLink` | Optional study identifier, PACS study ID, viewer URL and verification flag, linked to one order. This is a record for a study link, not proof of a live PACS connection. |
| `AuditEvent` | Actor (when known), action, entity type/ID, optional JSON details and creation time. |

Important uniqueness rules include a unique patient number, user email, order accession number, one report per order, one study link per order, unique non-null study instance UID and unique invitation token hash. The Prisma schema also defines indexes used for common status, date, patient and audit lookups.

The current schema does not include a patient login account relationship, medication/allergy records, pharmacy stock, prescriptions or contrast-agent inventory records.

## 6. API reference

All API paths below are mounted under `/api`, except the root, health and Swagger documentation paths. Protected endpoints require:

```http
Authorization: Bearer <access-token>
```

### System and authentication

| Method | Path | Access | Purpose |
|---|---|---|---|
| GET | `/api/health` | Public | API/database health check |
| POST | `/api/auth/login` | Public | Staff login |
| GET | `/api/auth/me` | Authenticated | Return current user |
| POST | `/api/auth/accept-invitation` | Public, token required in body | Activate an invited staff account |

### Dashboard

| Method | Path | Access | Purpose |
|---|---|---|---|
| GET | `/api/dashboard/summary` | Authenticated staff roles | Return database-backed statistics and the next appointments |

### Patients

| Method | Path | Access | Purpose |
|---|---|---|---|
| POST | `/api/patients` | Admin, Receptionist | Register patient |
| GET | `/api/patients` | Authenticated | List/search patients; supports `page`, `limit`, `search` |
| GET | `/api/patients/:id` | Authenticated | Patient details, appointments and orders |
| PATCH | `/api/patients/:id` | Admin, Receptionist | Update patient demographics/contact details |

### Appointments

| Method | Path | Access | Purpose |
|---|---|---|---|
| POST | `/api/appointments` | Admin, Receptionist | Schedule appointment |
| GET | `/api/appointments` | Authenticated | List appointments; supports pagination, patient, modality, status and date filters |
| GET | `/api/appointments/:id` | Authenticated | Appointment details |
| PATCH | `/api/appointments/:id` | Admin, Receptionist | Reschedule/update appointment details |
| PATCH | `/api/appointments/:id/status` | Admin, Receptionist, Technician | Change appointment status using allowed transitions |

### Radiology orders

| Method | Path | Access | Purpose |
|---|---|---|---|
| POST | `/api/radiology-orders` | Admin, Receptionist | Create order |
| GET | `/api/radiology-orders` | Authenticated | List/filter orders; supports pagination, patient, appointment, modality, priority and status |
| GET | `/api/radiology-orders/:id` | Authenticated | Order, patient, appointment, report and study-link details |
| PATCH | `/api/radiology-orders/:id/status` | Admin, Technician | Normal status transition |
| PATCH | `/api/radiology-orders/:id/status/override` | Admin | Administrative status correction with reason |

### Radiology reports

| Method | Path | Access | Purpose |
|---|---|---|---|
| POST | `/api/radiology-reports` | Radiologist | Create a draft for a completed order |
| GET | `/api/radiology-reports` | Admin, Radiologist | List/filter reports; supports pagination, order and status |
| GET | `/api/radiology-reports/:id` | Admin, Radiologist | Report details |
| PATCH | `/api/radiology-reports/:id` | Radiologist | Edit own draft |
| PATCH | `/api/radiology-reports/:id/review` | Radiologist | Review another radiologist's draft |
| PATCH | `/api/radiology-reports/:id/finalize` | Radiologist | Finalize a reviewed report |

### Staff invitations

| Method | Path | Access | Purpose |
|---|---|---|---|
| POST | `/api/staff/invitations` | Admin | Create staff invitation; response includes the one-time invitation URL |
| GET | `/api/staff/invitations` | Admin | List/filter invitations; supports pagination, status and email |
| PATCH | `/api/staff/invitations/:id/revoke` | Admin | Revoke a pending invitation |

Swagger UI is available at `/api-docs` when the backend is running. Use it as the interactive reference for the exact request schemas and response examples in the running build.

## 7. Common response shape

Successful API responses use a `success` flag and, where applicable, a `data` property. List endpoints also return pagination information. Error responses use `success: false` and a message. The API uses standard HTTP status codes, including `200`, `201`, `400`, `401`, `403`, `404`, `409` and `503` depending on the route and failure.

Do not assume that every endpoint accepts the same fields. The Zod schemas in each backend module define the accepted request fields and limits.
